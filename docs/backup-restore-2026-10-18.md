## 隔离导入执行方案

`scripts/restore_mysql_drill.py` 使用 Python 3 标准库与现有 Docker CLI。它复核 SHA-256 和 gzip，再读取原 MySQL 容器的不可变镜像 ID，创建独立临时容器：

- 不拉取镜像，不加入生产网络，不发布端口，不挂载生产数据卷。
- 配置 768 MiB 内存/内存加 Swap 总限额、0.75 CPU、256 进程上限；关闭性能统计，缓冲池设为 64 MiB。
- 随机生成独立的临时 root 密码，只通过环境变量传入；不将密码、SQL 内容或原始错误输出打印到终端。
- 导入前检查目标身份、所有权标签、镜像、网络、端口、资源限制及挂载来源，确认目标不是生产实例。
- 通过 TCP 等待最终 MySQL 就绪，避免把初始化过程中的临时服务误当成可导入实例。
- 导入后列出所有业务表的精确行数，检查核心表存在，并检查负现金、负持仓、账户缺失用户及成交缺失委托四类基础异常。
- 保存 `restore-run-*/restore-state.json`，权限受 `umask 077` 保护。成功时保留临时容器供下一步应用读取核验；失败时仅尝试停止本次创建且标签匹配的容器，保留独立测试数据供诊断。

本地保护逻辑测试通过不等于服务器真实恢复成功。完成上述脚本只应记录“隔离导入及基础检查通过”；完整账户对账、更多关联校验、应用认证读取和临时环境清理仍待后续验证。

本轮本地验证：`backend/tests/test_restore_drill.py` 的 17 项测试通过，覆盖校验失败时禁止启动容器、拒绝生产实例/生产挂载/非隔离网络、导入失败只停止自有临时容器，以及错误输出不泄漏凭据；Python 语法与 `git diff --check` 通过。真实导入结果已由用户回传，见下方记录。

- 使用恢复库中的临时测试会话，逐个读取 ACTIVE 用户的账户、持仓、委托、成交，并与恢复库原数据比较，验证列表归属。
